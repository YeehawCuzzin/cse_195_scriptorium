[NarrativeText]
Document parsing is a foundational component of retrieval-augmented generation (RAG) sys- tems, yet it is often treated as a minor prepro- cessing step. In research-focused systems such as Scriptorium / RefAIned, parser choice af- fects chunking, embedding quality, retrieval coherence, citation traceability, and the preser- vation of scholarly document structure. This re- port extends an earlier retrieval-oriented parser evaluation into a reproducible CSE 195 inges- tion benchmark.

[NarrativeText]
We implement a modular parser framework that standardizes execution across nine local PDF parsers: PyMuPDF, pdfplumber, PyPDF, Apache Tika, Unstructured, Docling, Marker, MinerU, and GROBID. The framework uses a shared parser registry, individual parser wrap- pers, a common extract(pdf_path) inter- face, normalized text outputs, artifact track- ing, and benchmark status reporting. On an IEEE-style scientific PDF, all nine parsers suc- cessfully execute in the stabilized JupyterHub environment. The benchmark records runtime, extracted character count, output file inventory, and qualitative output previews.

[NarrativeText]
The results show a clear tradeoff between speed and structural richness. Flat text parsers such as PyMuPDF, PyPDF, and pdfplumber run quickly but provide limited structural preserva- tion. Structure-aware parsers such as Docling, Marker, and MinerU produce richer Markdown, layout, image, and artifact outputs at higher runtime cost. GROBID extracts less total text but provides academically useful metadata- oriented structure. The benchmark also doc- uments excluded parsers, including Nougat and PaddleOCR, whose dependency or runtime con- straints made them unsuitable for the stable shared environment. Overall, this work pro- vides a reproducible ingestion baseline for fu- ture retrieval, chunking, citation, and traceabil- ity experiments in Scriptorium. [Title]
Introduction

[NarrativeText]
Large Language Models (LLMs) have become central to modern NLP systems (Vaswani et al., 2017; Devlin et al., 2019), especially in retrieval- augmented generation (RAG) pipelines where ex- ternal documents are used to improve factual grounding and contextual relevance. In these sys- tems, document ingestion is not a neutral prepro- cessing step. The way a PDF is parsed determines what text, metadata, headings, tables, figures, and citations are available to downstream chunking and retrieval components.

[NarrativeText]
Scientific PDFs are particularly challenging be- cause they often contain multi-column layouts, page headers and footers, section hierarchies, equa- tions, figures, tables, and references. Flat text ex- traction can lose this structure, merge unrelated regions, or introduce spacing artifacts. These er- rors can then propagate into chunks, embeddings, search results, and generated answers. Document parsing research therefore emphasizes that useful parsing should preserve structural relationships, semantic organization, and machine-readable rep- resentations such as Markdown, JSON, or XML rather than merely transcribing text (Zhang et al., 2024).

[NarrativeText]
This CSE 195 project focuses on Scriptorium / RefAIned, a research-oriented ingestion and re- trieval system. The goal is to move beyond ad hoc parser testing and create a reproducible bench- mark that can support evidence-backed parser se- lection. This report updates the earlier CSE 188 parser evaluation by shifting the emphasis from a small retrieval experiment to a reusable ingestion infrastructure. Instead of only asking which parser gives better retrieved chunks, this work asks how a practical system can consistently run, compare, and inspect multiple parsers under a shared framework.

[NarrativeText]
The contributions of this report are as follows:

[ListItem]
We implement a modular parser benchmark with a shared registry, standardized parser wrappers, normalized outputs, and parser sta- tus reporting.

[ListItem]
We successfully run nine local parsers on the same scientific PDF: PyMuPDF, pdfplumber, PyPDF, Tika, Unstructured, Docling, Marker, MinerU, and GROBID.

[ListItem]
We compare parser outputs by extracted char- acter count, runtime, artifact production, and qualitative output previews.

[ListItem]
We document excluded tools and environment constraints, including Nougat, PaddleOCR, Uni-Parser / Uniparser, and PyMuPDF4LLM.

[ListItem]
We identify next steps for retrieval-focused evaluation, including chunking comparisons, top-k retrieval tests, and structure preservation metrics.

2 Background and Motivation

[Title]
2.1 Document Parsing for RAG

[NarrativeText]
RAG systems typically include document loading, parsing, chunking, embedding, retrieval, and gen- eration. Many systems focus on the embedding model or retrieval algorithm, but parser output qual- ity strongly shapes what information is available before embedding begins. If a parser loses head- ings, splits tables incorrectly, duplicates headers, or merges columns, those artifacts become part of the retrieval corpus.

[NarrativeText]
Document parsing can be viewed as a spectrum. At one end are flat text extractors that recover text quickly with limited structural awareness. In the middle are semi-structured extractors that produce readable text but still preserve limited document hierarchy. At the other end are structure-aware parsers that attempt to preserve sections, tables, figures, metadata, layout information, and artifacts. This distinction matters for research PDFs because the most useful context is often tied to structure, not just raw text.

[Title]
2.2 From CSE 188 Evaluation to CSE 195

[Title]

5.2 Character Count Comparison

[NarrativeText]
Character count provides a rough indication of ex- traction coverage, but it is not a direct quality met- ric. Higher character count may indicate more complete extraction, but it may also include du- plicated headers, noisy OCR output, references, captions, or formatting artifacts. In the final run, Marker produced the most text, followed by Do- cling and Unstructured. GROBID produced the least text, which is expected because it emphasizes scholarly document structure and metadata rather than maximizing raw text volume.

[Title]
5.3 Runtime Comparison

[NarrativeText]
The runtime comparison shows a clear tradeoff between simple extraction and heavier structure- aware parsing. PyMuPDF, Tika, and PyPDF were the fastest. Marker and MinerU were the slowest because they perform more expensive document analysis and produce additional artifacts.

6 Qualitative Findings

[Title]
6.1 Flat Text Parsers

[NarrativeText]
PyMuPDF, pdfplumber, and PyPDF are useful baselines because they are fast and simple. How- ever, they provide limited structural preservation. They may lose heading hierarchy, merge text across columns, or flatten tables and figures. pdfplumber in particular can preserve some layout signals but is sensitive to multi-column formatting and spacing artifacts.

[Title]
6.2 Tika

[NarrativeText]
Tika provides a semi-structured baseline and runs quickly once Java is available. It produces readable text and can handle document-level extraction, but it does not preserve rich scholarly structure or arti- fact outputs in the same way as modern structure- aware parsers.

[Title]
6.3 Unstructured

[NarrativeText]
Unstructured provides element-level labels such as headers, narrative text, and plain text. This makes it more useful than flat extraction for down- stream chunking because chunks can potentially be

[NarrativeText]
aligned with document elements rather than arbi- trary character ranges.

[Title]
6.4 Docling

[NarrativeText]
Docling provides a strong balance between struc- tural output and runtime. It produced one of the highest character counts while remaining much faster than Marker and MinerU. Its Markdown- style output makes it useful for RAG pipelines that benefit from headings and readable structure.

[Title]
6.5 Marker

[NarrativeText]
Marker produced the largest normalized text output and generated additional artifacts. Its output pre- served Markdown formatting and extracted images. The tradeoff is runtime: Marker was the slowest parser in the final benchmark. It is useful when richer structure and artifact extraction are more important than speed.

[Title]
6.6 MinerU

[NarrativeText]
MinerU required the most setup work but success- fully ran using the txt method and pipeline back- end. It produced Markdown, JSON, images, layout PDFs, and other artifacts. MinerU is valuable for layout-aware parsing and multimodal-ready inges- tion, though it has higher runtime and environment complexity.

[Title]
6.7 GROBID

[NarrativeText]
GROBID produced fewer total characters than the other parsers, but it is valuable for academic meta- data and scholarly document structure. It extracts title, authors, references, and structured academic text. Its main tradeoff is that it requires a running service at localhost:8070.

[Title]
7 Excluded Parsers and Environment

[Title]
Constraints

[Title]
7.1 Nougat

[NarrativeText]
Nougat was tested and produced .mmd output, but it required older dependency pins, especially an older transformers version. That conflicted with the modern parser stack used by Docling, Marker, and MinerU. It was removed from the final benchmark to preserve a clean 9/9 stable run.

[Title]
7.2 PaddleOCR

[NarrativeText]
PaddleOCR was considered as an OCR/layout base- line. It installed and downloaded model files, and PDF pages were successfully rendered to images

[NarrativeText]
with PyMuPDF. However, runtime inference failed in the JupyterHub environment due to a PaddlePad- dle backend issue. Because it required separate environment isolation, it was excluded from the stable benchmark.

[Title]
7.3 Uni-Parser / Uniparser

[NarrativeText]
The originally linked cjm-sfw/Uniparser project was not a PDF parser. It focused on image/human parsing. A separate document-oriented Uni-Parser exists in the literature and is relevant as future work, but no simple local CLI or package was available for this benchmark.

[Title]
7.4 PyMuPDF4LLM

[NarrativeText]
PyMuPDF4LLM was considered but excluded be- cause it overlaps heavily with PyMuPDF. Since the benchmark already includes PyMuPDF as a flat text baseline, adding PyMuPDF4LLM would not add a sufficiently distinct parser category.

[Title]
8 Connection to Scriptorium Roadmap

[NarrativeText]
This benchmark supports the broader Scripto- rium roadmap by turning parser selection into an evidence-backed engineering decision. A research- focused RAG system needs more than raw ex- tracted text. It needs reliable ingestion, metadata, source traceability, reproducibility, and clear trade- offs between runtime and structure preservation.

[NarrativeText]
The parser benchmark establishes a foundation for future Scriptorium work in three ways. First, it provides a standardized framework for adding or removing parsers. Second, it saves normalized outputs and artifacts that can be reused for chunk- ing and retrieval experiments. Third, it documents environment constraints so future development can decide when parser isolation is necessary.

10 Conclusion

[NarrativeText]
This project demonstrates that document parsing should be treated as a first-class component of research-focused RAG infrastructure. The final benchmark successfully runs nine local parsers under a standardized interface and records output coverage, runtime, artifacts, and qualitative differ- ences. The results show that flat text parsers are fast and useful baselines, while structure-aware parsers provide richer outputs that are better aligned with downstream retrieval and traceability needs.

[NarrativeText]
The benchmark also shows that parser selection is not only a quality question but an infrastruc- ture question. Some tools require Java services, some require model inference, and some introduce dependency conflicts. By documenting these trade- offs and creating a reproducible benchmark, this work provides a practical foundation for future Scriptorium experiments in chunking, retrieval, ci- tation grounding, and source-aware document in- telligence.
